| RR-001 | Prompt Injection via Malicious CVE Data | An adversary embeds prompt injection payloads inside CVE description fields in the CVE database. When the Vulnerability Agent processes these entries, the injected instructions override the agent's system prompt, causing it to fabricate vulnerability scores, exfiltrate data, or issue unauthorized commands to the Orchestrator. | Vulnerability Agent, Orchestrator | 4 | 5 | **20 — Critical** | LLM01 – Prompt Injection | AML.T0051 (LLM Prompt Injection) | SI-10 (Information Input Validation), SI-3 (Malicious Code Protection), AC-4 (Information Flow Enforcement) | Input sanitization on CVE field ingestion; Orchestrator validates agent output schema | High (15) | 1. | RR-002 | Training / Context Data Poisoning via TI Feeds | A compromised or malicious threat intelligence feed provider injects false TTP mappings, fabricated threat actor profiles, or misleading ATLAS technique attributions. The Threat Intel Agent ingests these as ground truth, causing the system to produce a risk assessment that misses real threats or assigns incorrect mitigations. | Threat Intel Agent, Orchestrator | 3 | 5 | **15 — High** | LLM03 – Training Data Poisoning | AML.T0020 (Poison Training Data), AML.T0018 (Backdoor ML Model) | SR-6 (Supplier Assessments and Reviews), SI-7 (Software, Firmware, and Information Integrity), RA-3 (Risk Assessment) | TI feed sourced from vetted commercial providers; contractual SLAs in place | Medium (9) | 1. Cross-validate TI data across a minimum of two independent feed sources before accepting any TTP attribution. 2. Implement cryptographic integrity verification (signed feeds) for all TI ingestion. 3. Maintain an allowlist of known-good ATLAS technique IDs; flag any novel or unrecognized IDs for human review. 4. Conduct quarterly supplier risk assessments of all TI feed vendors per NIST SR-6. |
| RR-003 | Excessive Agent Autonomy / Scope Creep | The Orchestrator agent, tasked with coordinating the workflow, begins making autonomous decisions beyond its defined scope — such as triggering remediation actions, modifying CMDB records, or initiating external communications — without human authorization. This violates the least-privilege design and could cause unintended operational changes. | Orchestrator | 3 | 5 | **15 — High** | LLM08 – Excessive Agency | AML.T0047 (ML-Enabled Product Compromise) | AC-6 (Least Privilege), AU-12 (Audit Record Generation), CM-7 (Least Functionality) | Orchestrator access is scoped to READ and inter-agent messaging; WRITE is restricted to the Report Generator only | Medium (9) | 1. Enforce hard-coded action allowlists in the Orchestrator's execution environment — any action not on the list is blocked at the infrastructure layer, not just the prompt layer. 2. Implement a separate policy enforcement layer (e.g. OPA/Rego) that intercepts and validates every action the Orchestrator attempts before execution. 3. Alert on any Orchestrator attempt to call an API endpoint outside its registered tool set. 4. Conduct red-team exercises specifically targeting Orchestrator scope expansion. |
| RR-004 | Insecure Inter-Agent Communication | Messages passed between agents (e.g. Orchestrator → Vulnerability Agent → Control Mapping Agent) are transmitted without mutual authentication or integrity verification. An attacker with network access could perform man-in-the-middle attacks, injecting false vulnerability data into the inter-agent pipeline and corrupting the final risk assessment without detection. | All Agents | 3 | 4 | **12 — High** | LLM09 – Misinformation (via corrupted data flow) | AML.T0043 (Craft Adversarial Data) | SC-8 (Transmission Confidentiality and Integrity), IA-3 (Device Identification and Authentication), SC-28 (Protection of Information at Rest) | Internal network segmentation; TLS on external API calls | Medium (8) | 1. Implement mutual TLS (mTLS) for all inter-agent API calls, even within the internal network. 2. Sign all agent message payloads with HMAC-SHA256 and verify signatures at every receiving agent. 3. Assign unique cryptographic identities to each agent; rotate credentials on a defined schedule. 4. Deploy a service mesh (e.g. Istio) to enforce zero-trust networking between agents at the infrastructure layer. |
| RR-005 | Hallucinated Vulnerability Assessment Data | The Vulnerability Agent, relying on an LLM to interpret and contextualize CVE data, generates plausible-sounding but factually incorrect CVSS scores, affected system mappings, or exploitation likelihood assessments. These hallucinations propagate to the risk register and executive report, causing the organization to misallocate remediation resources. | Vulnerability Agent, Report Generator | 4 | 4 | **16 — High** | LLM09 – Overreliance / Misinformation | AML.T0048 (Erode ML Model Integrity) | RA-5 (Vulnerability Monitoring and Scanning), SI-12 (Information Management and Retention), CA-7 (Continuous Monitoring) | Agent instructed to cite source CVE IDs; output reviewed by human approver | Medium (10) | 1. Require the Vulnerability Agent to ground every claim with a direct CVE ID reference; any claim without a traceable source is flagged as unverified. 2. Implement a retrieval-augmented generation (RAG) pattern where the agent retrieves the raw CVE record and annotates it rather than generating from memory. 3. Run automated cross-checks comparing agent-generated CVSS scores against the NVD API score for the same CVE ID. 4. Add a "confidence score" field to all agent outputs; low-confidence outputs are held for mandatory human review before inclusion in the report. |
| RR-006 | Unauthorized CMDB Access / Data Exfiltration | The Asset Context Agent is granted READ access to the CMDB. If the agent's credentials are compromised (e.g. via prompt injection or token leakage in logs), an attacker could exfiltrate the full asset inventory including IP ranges, system owners, software versions, and network topology — providing a complete attack map of the organization. | Asset Context Agent | 3 | 5 | **15 — High** | LLM06 – Sensitive Information Disclosure | AML.T0040 (ML Model Inference API Access) | AC-2 (Account Management), AC-17 (Remote Access), AU-2 (Event Logging), IA-5 (Authenticator Management) | Scoped read-only API token; network access controls on CMDB endpoint | Medium (9) | 1. Issue a scoped, time-limited API token to the Asset Context Agent with access restricted to only the specific CMDB fields required (asset name, classification tier, owner — not full network topology). 2. Enable query-level audit logging on the CMDB; alert on any query that returns more than a threshold number of records in a single call. 3. Implement attribute-based access control (ABAC) so the agent can only retrieve records tagged as "in-scope for risk assessment". 4. Store agent credentials in a secrets manager (e.g. HashiCorp Vault) with automatic rotation; never persist tokens in agent logs or memory. |
| RR-007 | Report Tampering Before Human Approval | Between the Report Generator Agent writing the draft report and the Security Manager reviewing it in the human approval gate, an attacker with write access to the report staging area modifies risk scores, removes critical findings, or alters recommended mitigations. The Security Manager approves the tampered report, believing it is the agent-generated output. | Report Generator, Human Approval Gate | 2 | 5 | **10 — High** | LLM02 – Insecure Output Handling | AML.T0043 (Craft Adversarial Data) | AU-10 (Non-Repudiation), SC-28 (Protection of Information at Rest), SI-7 (Software, Firmware, and Information Integrity), AC-3 (Access Enforcement) | Report stored in access-controlled repository; Security Manager reviews via internal portal | Low–Medium (6) | 1. Generate a cryptographic hash (SHA-256) of the report immediately upon creation by the Report Generator; store this hash in an append-only audit log that neither the staging system nor any user can modify. 2. Display the hash to the Security Manager alongside the report in the approval UI; require them to confirm the hash matches before signing off. 3. Apply digital signatures to the report file at generation time using an asymmetric key held by the Report Generator's execution environment. 4. Restrict write permissions on the report staging area to only the Report Generator service account; all human reviewer access is READ-only. |
| RR-008 | Human Approval Gate Bypass | An adversary or a misconfigured automation workflow circumvents the human approval requirement — for example, by triggering the report delivery pipeline directly, exploiting a race condition in the workflow state machine, or using social engineering to obtain approval without genuine review. Reports are distributed to stakeholders without proper security manager sign-off. | Orchestrator, Human Approval Gate | 2 | 5 | **10 — High** | LLM08 – Excessive Agency | AML.T0047 (ML-Enabled Product Compromise) | AC-5 (Separation of Duties), CM-3 (Configuration Change Control), AU-6 (Audit Record Review, Analysis, and Reporting) | Approval gate implemented as a mandatory workflow step; no automated bypass path documented | Low–Medium (6) | 1. Implement the approval gate as a cryptographic signing requirement — the final report cannot be decrypted or distributed without the Security Manager's private key signature; technical enforcement, not just process enforcement. 2. Separate the approval authority from the report generation pipeline at the infrastructure level (different service account, different network segment). 3. Generate an immutable audit log entry for every approval action including approver identity, timestamp, and report hash. 4. Configure the workflow to require dual approval (Security Manager + one additional reviewer) for reports with a Critical-rated risk. |
| RR-009 | Supply Chain Compromise of Threat Intelligence Feeds | A nation-state actor or sophisticated threat group compromises the upstream TI feed provider and injects strategically false threat actor attributions, fabricated TTPs, or deliberately omits indicators of an ongoing campaign. The Threat Intel Agent processes this as legitimate data, and the resulting risk assessment fails to flag an active threat targeting the organization. | Threat Intel Agent | 2 | 5 | **10 — High** | LLM03 – Training Data Poisoning | AML.T0018 (Backdoor ML Model), AML.T0020 (Poison Training Data) | SR-3 (Supply Chain Controls and Plans), SR-6 (Supplier Assessments), SI-7 (Software, Firmware, and Information Integrity), RA-3 (Risk Assessment) | Single commercial TI feed subscription; provider SOC 2 Type II certified | Medium (8) | 1. Subscribe to a minimum of three TI feeds from independent providers and implement a consensus mechanism — TTPs appearing in only one feed require additional human validation before inclusion. 2. Integrate free/open-source feeds (e.g. MISP community, AlienVault OTX) as a cross-check layer alongside commercial feeds. 3. Monitor for sudden changes in feed content patterns (e.g. a feed that historically reported 20 IOCs/day suddenly reporting 0 or 500) as an anomaly signal. 4. Establish an incident response procedure for TI feed compromise scenarios including the ability to roll back to a last-known-good feed snapshot. |
| RR-010 | Model Inversion / Membership Inference Attack | An adversary with query access to the Vulnerability Agent or Threat Intel Agent submits carefully crafted queries designed to infer what specific vulnerability data, system configurations, or asset details were in the agent's context window or training data. This could reveal sensitive information about the organization's security posture without directly breaching the CMDB. | Vulnerability Agent, Threat Intel Agent, Asset Context Agent | 2 | 4 | **8 — Medium** | LLM06 – Sensitive Information Disclosure | AML.T0040 (ML Model Inference API Access), AML.T0024 (Exfiltration via ML Inference API) | AC-20 (Use of External Systems), AU-13 (Monitoring for Information Disclosure), SC-7 (Boundary Protection) | Agents not exposed to external users; internal access only | Low (4) | 1. Implement strict query rate limiting on all agent APIs to slow inference attacks. 2. Apply differential privacy techniques when agents return aggregate statistics or summaries. 3. Ensure agents operate on session-scoped context windows that are cleared after each task; no persistent memory of prior assessment runs that could be probed. 4. Monitor query patterns for systematic probing behavior (many similar queries with slight variations) and trigger alerts. |
| RR-011 | LLM Jailbreak Enabling Policy Bypass | An insider or compromised upstream system crafts a sophisticated multi-turn jailbreak sequence targeting one of the LLM-backed agents — particularly the Orchestrator or Control Mapping Agent — causing it to ignore its system-level safety instructions and operate outside its intended security policy, potentially approving risks it should escalate or recommending insufficient controls. | Orchestrator, Control Mapping Agent | 3 | 4 | **12 — High** | LLM01 – Prompt Injection, LLM08 – Excessive Agency | AML.T0054 (LLM Jailbreak) | SI-10 (Information Input Validation), CM-6 (Configuration Settings), AC-6 (Least Privilege) | System prompts include refusal instructions; conversation logs reviewed | Medium (8) | 1. Implement a constitutional AI / system-level policy layer that is evaluated independently from the main LLM inference — policy compliance is checked by a separate model, not self-assessed. 2. Limit agent context windows to task-relevant information only; do not pass full conversation history between tasks (reduces multi-turn jailbreak surface). 3. Deploy automated red-teaming (e.g. using an adversarial LLM) against agent system prompts on a scheduled basis to proactively discover jailbreak vectors. 4. Treat any agent output that recommends "skipping a control," "bypassing approval," or "accepting all risks" as a mandatory escalation trigger regardless of the stated rationale. |
| RR-012 | Insecure Logging of Sensitive Assessment Data | Agent logs, used for debugging and audit purposes, inadvertently capture sensitive data including full asset inventories from the CMDB, raw CVE exploitation details, or threat actor TTP specifics. If log infrastructure is compromised or logs are accessible to unauthorized parties, this creates a secondary exfiltration path for the organization's complete security posture. | All Agents | 3 | 4 | **12 — High** | LLM06 – Sensitive Information Disclosure | AML.T0040 (ML Model Inference API Access) | AU-3 (Content of Audit Records), AU-9 (Protection of Audit Information), SC-28 (Protection of Information at Rest) | Logs stored in SIEM; access restricted to security ops team | Medium (8) | 1. Implement log scrubbing at the agent output layer — PII, IP addresses, system names, and CVE payload details are redacted before writing to logs. 2. Use structured logging with field-level classification tagging; Restricted fields are only written to encrypted, access-controlled log tiers. 3. Apply the principle of least log — log agent decisions and outcomes, not the full data payloads processed. 4. Encrypt all log data at rest and enforce log access via role-based controls with just-in-time access provisioning. |

## Glossary

| Term | Definition |
|------|-----------|
| CVSS | Common Vulnerability Scoring System — standardized method for rating IT vulnerability severity |
| CMDB | Configuration Management Database — repository of IT asset information |
| TTP | Tactics, Techniques, and Procedures — adversary behavior patterns |
| ATLAS | Adversarial Threat Landscape for Artificial-Intelligence Systems (MITRE) |
| RMF | Risk Management Framework (NIST SP 800-37) |
| LLM | Large Language Model |
| mTLS | Mutual Transport Layer Security |
| RAG | Retrieval-Augmented Generation |
| IOC | Indicator of Compromise |
